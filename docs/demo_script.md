# PulseBrief Demo 脚本

目标时长：4–5 分钟。默认从 C 端体验模式开始，最后切到开发者模式展示 Harness。

---

## 0:00–0:30 开场

**操作**：打开 Streamlit 首页。

**说**：

> 这是一个个人健康简报 Agent。用户上传一段时间的穿戴数据，它会找出睡眠和活动的变化，生成一份一周计划；只有用户确认后才会创建任务，创建完还会回数据库核对。
>
> 默认界面是给普通用户看的单页流程；底层仍然是完整的 Agent Harness。工程师可以在侧边栏打开开发者模式，看到每一步工具调用、审批和验证记录。

---

## 0:30–1:00 载入示例数据

**操作**：点击 **用示例数据体验**。

**说**：

> 这里用 35 天模拟数据，不涉及真实个人健康信息。数据先经过校验：缺失、重复日期、非法数值、天数不足都会被识别，不会被静默填成 0。
>
> 首页先给出一个概览：平均睡眠、日均步数、平均静息心率。用户不用理解 CSV 字段，也能知道数据大概是什么样。

---

## 1:00–1:45 生成简报

**操作**：点击 **生成我的健康简报**，等待完成。

**说**：

> Agent 现在自主决定工具顺序：检查数据完整性、对四个指标做最近 7 天与此前 7 天的趋势对比、读取用户目标与每日可用时间，然后生成计划并做确定性校验。
>
> 这些数字全部来自 Python 计算，不是模型估的。上下文里没有原始 CSV，模型需要数据时再通过工具查询。

**状态变为计划确认页**。

---

## 1:45–2:30 计划与审批

**操作**：展示 4 张计划卡，然后点击 **好，创建这 4 个任务**。

**说**：

> 这是 Agent 建议的 4 件小事：固定就寝、午后步行、睡前拉伸、记录睡眠感受。每项都有频率、时长和开始日期，并且经过了时间预算与低强度偏好的校验。
>
> 注意这里必须由我确认。审批不是 Prompt 里写一句“记得问用户”，而是 Harness 暂停、写工具二次校验审批记录和计划 hash。批准只对这一次、这一份计划有效。

**批准后展示成功提示**。

**说**：

> 写入完成后，它重新查询 SQLite，确认任务数量、ID、字段、日期、状态和审批消费都正确，才显示“已创建并通过校验”。

---

## 2:30–3:15 健康简报

**操作**：展示 4 张信号卡与计划卡。

**说**：

> 对普通用户来说，他看到的不是 trace 和 JSON，而是四张卡：睡眠、日常活动、运动、恢复状态，以及一句人话总结。
>
> 比如这里睡眠比前一周少了 0.7 小时、步数少了约 700 步、运动时长几乎减半，所以建议从固定就寝和午后散步开始，而不是一次性全部改变。
>
> 技术细节收在「Agent 做了什么」里，展开可以看到检查数据、分析指标、校验计划、创建任务、核对写入。

---

## 3:15–4:00 开发者模式

**操作**：打开侧边栏 **开发者模式**，进入 `执行轨迹`。

**说**：

> 这是给工程师和面试官看的视角：每一步 LLM / Tool / Approval / Verification 都有输入、输出摘要、状态、耗时和重试次数。
>
> 我们刻意不展示模型内部推理，只展示可观察的执行事实。这里也能看到审批是 PENDING、APPROVED 还是 CONSUMED，以及最终的数据库校验结果。

**可选**：切到 `任务与审批` 展示真实任务与审批历史。

---

## 4:00–4:45 评估

**操作**：切到 `评估`，点击 **运行完整评估**。

**说**：

> 27 个用例，覆盖正常、缺失、非法、数据不足、工具失败、恢复、审批、权限、重复写入和安全。每个用例用独立 SQLite，走真实工具与审批路径。
>
> 最重要的指标是 Unauthorized Write Count，必须为 0。其他还包括工具选择准确率、指标计算准确率、恢复率和验证准确率。所有断言由代码计算，不由模型自评。

**展示结果**：

> 当前 27/27 通过，未授权写入 0。

---

## 4:45–5:00 收尾

**说**：

> 这个项目想说明的是：Agent 不只是会回答问题，而是能在明确的环境、状态、工具、权限和反馈机制下完成有实际结果的任务；同时，产品表面可以很轻，底层的控制与验证必须很实。

---

## 备用演示：数据不合法

1. 回到体验模式，点击 **换一份数据**。
2. 上传 `data/fixtures/missing_sleep.csv`。
3. 页面显示“这份数据暂时不能用”，列出空值与日期缺口。

**说**：

> 这就是“不允许把无法确认的数据静默处理成正常值”。它不会为了完成任务而编造趋势，也不会进入计划生成。

---

## 备用演示：工具失败恢复

1. 开发者模式 → `评估`，查看 `tool_transient_failure` 与 `write_transient_failure`。
2. 进入 `执行轨迹` 查看 `retry_count > 0` 的记录。

**说**：

> 工具超时或异常时，Harness 最多重试一次；持续失败会降级分析并明确说明哪个指标不可用。

## 常见提问

**Q：这是 C 端产品还是工程 Demo？**
A：默认表面是 C 端体验，底层是 Harness 工程 Demo。产品层负责让普通用户看懂结论和计划；开发者模式负责证明每一步可控、可验证、可观察。

**Q：审批为什么不能只写在 Prompt 里？**
A：Prompt 是建议，不是权限。审批是数据库记录 + payload hash + 工具内校验，模型无法绕过。

**Q：如何防止重复创建任务？**
A：计划规范化后计算 batch key，`(idempotency_key, task_index)` 唯一；重复提交返回已有任务，不新增。

**Q：如何保证报告里的数字是真的？**
A：数字只来自工具输出；写操作后回读 SQLite 验证；最终答复基于验证结果生成。

**Q：真实模型效果如何？**
A：仓库提供 OpenAI 兼容适配层；离线评估验证的是 Harness 与工具链，不代表某个模型的能力。接入真实模型后应重新跑评估并记录 Token 与延迟。
